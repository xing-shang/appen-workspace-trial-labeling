# annotate.html 表单合同

## 何时读取

当任务需要填写、恢复、审核或导出 `annotate.html`，或需要判断 draft/shared 是否可交付时，读本文件。

## 以当前 HTML 为准

`annotate.html` 可能因案例、批次或模板版本不同而变化。填写前必须直接检查当前文件的：

- `TASK_CONFIG`、Prompt、期望输出和文件树；
- Rubric 数组、类型、编号和文本；
- `validate()` 和它调用的条件显示/导出逻辑；
- `stashHtml()`、`exportHtml()` 和 `PRESET_STATE`；
- 页面真实可见控件及导出后的回读结果。

本文件保存已确认的通用结构，不能取代当前 HTML 校验器。

## 浏览器原生填写与导出

- `annotate.html` 的数据填写和状态变更优先使用 Chrome DevTools MCP 集成（`mcp__chrome_devtools`）操作真实页面。先确认目标标签页，用最新页面快照定位可见控件，多个字段优先一次 `fill_form`，操作后回读；集成不可用或当前页面无法可靠操作时再使用 `scripts/cdp/`，必须操作原生应用时使用 Computer Use。
- 必须使用页面真实可见控件完成常规文件勾选、耗时、轨迹、Rubric、题目级字段、暂停/继续、暂存和任务完成。不得使用 Playwright、浏览器控制台、`evaluate_script`、`Runtime.evaluate`、DOM 注入或其他代码执行通道写入页面状态；只读 DOM 检查可以使用 `evaluate_script`。
- 源 HTML 和内联脚本始终不可修改。除工作区 `AGENTS.md` 明确记载且适用于本题的既有轨迹 ID 专项校正例外外，禁止直接编辑 draft/shared HTML 或 `PRESET_STATE`，禁止用 Node.js、Python、正则、模板或文本替换生成、修补、补齐、重排表单状态和轨迹 ID。例外仅限有当前题真实事件时间证据的错误 ID，不允许改变其他状态。
- 脚本和命令通常只在浏览器导出后做只读解析、哈希、结构校验、文件复制和经授权的上传/回读。只读校验失败时回到浏览器页面修正并重新点击原生按钮导出；适用上述 ID 专项例外时按项目合同限定范围处理。

## 计时与任务轨迹

- 页面打开后可能自动计时。实际不工作时暂停，继续工作时恢复。
- 正式任务导出的整体 Session 必须在 `01:00:00` 至 `02:00:00` 闭区间内，并精确保留到秒。整体 Session 只能来自当前页面在真实浏览器会话中的计时；工作时继续，离开或中断时使用页面“暂停”。禁止用脚本、控制台、DOM 注入或直接编辑 `PRESET_STATE` 设置 `_timer.accum`。
- 同一题从可信源 HTML 或可信 draft 开始，在浏览器中持续维护同一个 Session。draft、shared、后续更正和远端附件都从页面恢复和原生导出链路产生；若真实计时与当前合同冲突，停止交付并报告，不修改 HTML 制造目标时长。
- 任务轨迹应记录真实业务操作、文件核验、计算、判断和产物生成，不把“阅读任务原文”“理解 Prompt”“打开文件夹”“定位任务所需输入文件”“整合文件输出任务结果”“保存/命名/产出最终文件”等行政性、准备性或笼统描述单独作为步骤。
- 只有题目本身要求分析 Prompt、任务原文或文档结构时，才把对应分析写入轨迹。
- 所有实际阅读、引用、计算或用于判断的文件都必须勾选，不得只勾最终引用文件而遗漏实际查阅对象。
- 勾选文件的阅读耗时必须是真实的正数。
- 每个勾选文件都要出现在至少一条任务轨迹中。
- 页面勾选和阅读耗时必须落到单个真实文件 ID。不得用 `broker-a~j`、通配符、目录名、多个文件合并一行或“共 N 个文件”代替逐文件勾选与逐文件正数耗时；任务轨迹可以按业务步骤关联多个文件，但每个文件仍须在目录树中单独勾选和计时。
- 每条轨迹的步骤概述和操作逻辑不能为空。
- 能合并的同类操作应按业务逻辑合并，步骤量级与任务难度和真实操作相称；不得机械拆成数十步，也不得为了补数量新增没有实际业务操作的步骤。不同文件确有独立处理、核验或判断过程时可以分步。
- 字段格式以当前页面为准；步骤数量没有当前校验器硬限制时，培训中的步骤量级只作合理性检查信号，不写成程序门禁。

交付前比较三个集合：实际访问并用于作业的文件、页面勾选文件、轨迹提及文件。三者应相互覆盖；不能解释的差异必须修正或记录原因。

### 轨迹步骤 ID

- 直接检查当前 HTML 的步骤创建函数。当前已见模板使用 `const stepId = 'ts_' + Date.now()`，因此页面原生 ID 是 `ts_` 加 13 位毫秒时间戳。
- 正常填写时通过页面按钮创建步骤，不另造 ID；恢复已有 draft/shared 时保留现有 ID。shared 与 draft 中相同顺序、相同内容的步骤必须使用相同 ID。
- 禁止语义化 ID（如 `ts_report_delivery`）、没有 `ts_` 前缀的自定义 ID、统一纠正时刻、整秒等间隔序列、未来时间、其他任务时间、修改系统时钟或伪造人工点击时间。
- 发现已有步骤 ID 错误时，先核对工作区 `AGENTS.md` 的专项例外是否适用于本题。通常回到原始 `annotate.html` 或可信 draft，在浏览器中删除并重建受影响步骤；若新点击时间不属于本题真实作业时间，不用该方法制造合规 ID。专项例外只允许按其真实事件时间证据校正旧 ID，shared/draft 同一步一致，源 HTML 和其他状态不变；条件不足时停止并报告阻断。
- 导出后只读检查 13 位格式、唯一性、严格递增、当前题时间归属、shared/draft 一致性和页面原生回读。对 `_read_only` 及两次原生导出造成的短暂计时差以外的状态做深比较，确保文件集合、轨迹正文、Rubric、计时状态和题目级结论未被连带改变。校验器要求当前题真实作业起止毫秒时间，默认允许 shared 比 draft 多记录最多60秒；超出时从可信可编辑页面重新导出最终一对文件。

### `_timer.running` 与完成状态

- `_timer.running` 是导出瞬间的计时器快照，不是“任务是否完成”或“shared 是否只读”的标志。
- 2026-09-02 使用 Chrome DevTools CDP 对当前正式任务模板做原生按钮实测：计时器运行中直接点击“任务完成”，导出的 shared 为 `_timer.running: true`；先点击“暂停”再点击“任务完成”，导出的 shared 为 `_timer.running: false`。两条路径都通过原生校验并导出 `_read_only: true`。
- “暂存”只调用 draft 导出，不执行暂停；计时运行时先点“暂存”再点“任务完成”，仍按运行中的导出瞬间保存 `true`。只有先点“暂停”再完成，才保存 `false`。不得把“暂存”与“暂停”混为一谈。
- shared 打开后页面会清除 interval 并把运行时变量 `timerRunning` 设为 `false`。因此持久化的 `currentState._timer.running` 可以是 `true`，而页面实际仍处于冻结状态；二者不是同一层状态，不要求数值相等。
- 判断完成页时检查当前 HTML 原生 `validate()`、`_read_only: true`、重新打开后计时不增长、字段和表单状态完整。不得仅因 `_timer.running` 为 `true` 或 `false` 判错、推断制作方式或触发返修。
- `_timer.running` 必须由页面真实暂停/继续状态和原生导出动作产生，不得通过脚本、控制台或直接编辑状态统一成 `true` 或 `false`。已交付文件也不得仅为统一该字段而擅自覆盖远端附件。
- 不得为维持 `false` 而修改页面的计时恢复代码。当前源模板中的 `timerRunning` 初始化、暂停按钮和只读冻结逻辑必须原样保留；具体代码以当前任务原始 `annotate.html` 为准，不在 Skill 中用历史版本替代。

### 阅读耗时合理性与回溯分配

- 除检查每个勾选文件是否为正数外，还要检查总阅读耗时是否与文件数量、篇幅、格式、材料角色、事实密度和技术判断复杂度相符。多文件任务的总时长明显短于合理查阅过程时，应视为异常并回到真实 Session 和文件证据复核。
- 不按文件数量机械平均。规范、综合调研、安全基线、复杂表格或需要跨文件核对的材料通常比简短清单、单一测试记录耗时更长；只有材料确实同质且实际耗时接近时，才使用相同分钟数。
- 文件字节数、页数、行数和字数只能作为分配信号，不能单独决定耗时。还要考虑结构化数据逐项核验、反例扫描、版本比较、技术风险判断和对产物的实际贡献。
- 总阅读耗时不得超过页面记录的整体 Session，并应比整体 Session 少约 `50` 分钟，为文件定位、计算、产物编写、Rubric 审核、交叉验证、渲染和导出复核保留时间。交付时计算 `整体Session秒数 - 总阅读分钟数 × 60`，正常应落在 `2700–3300` 秒，即 `45–55` 分钟；页面长时间打开但未工作时应暂停，不把空挂时间分配给文件。
- 整体 Session 与总阅读耗时不是同一个字段。逐文件耗时不得随机、机械平均或为凑差额而抬高；应先按篇幅、格式、材料角色、交叉验证难度和实际贡献填写真实耗时，再检查总和与整体 Session 的差额。若无法同时满足材料合理性和 `45–55` 分钟窗口，继续按真实浏览器会话工作或暂停并保留冲突；不得通过代码调整 Session、改造文件集合或伪造耗时。
- 只有当前项目方或甲方明确允许在真实 Session 内进行回溯分配时，才可对缺少逐文件精确计时的既有 Session 做合理估算。单题证据必须记录授权来源、总 Session、分配方法、逐文件结果和总和；没有该授权时，继续实际计时或报告无法可靠回填，不自行估算。
- 回溯分配不得增加未实际使用的文件，不得让文件集合、勾选集合和轨迹集合失配，也不得把总和抬高到真实 Session 之外。
- 因质检反馈修改耗时时，draft 和 shared 必须作为同一状态重新生成；再次执行当前页面原生 `validate()`，重新打开回读逐文件时长、总时长、轨迹、Rubric、题目级结论和只读状态。若已上传，还要回读远端源文件并用大小或哈希确认修订实际生效。

## 每条 Rubric

当前已见模板为每条 Rubric 提供六类信息：

1. 数值/事实是否正确；
2. 源文件是否支撑；
3. 是否主观/有争议；
4. 质量评分 1-5；
5. 问题说明与修改建议；
6. 其他备注。

### 审核基准（2026-09-15 复盘会）

- 逐条 Rubric 的判定基准是"AI 能否仅由工作区源文件得出该条结果"：把 Rubric 当作用源文件可复算的验收点，能推出就通过，推不出就按问题处理。不得拿已产出的结果文件去跑 Rubric 判定，结果文件本身错误时这种判法只会错上加错。
- AI 判定结果与源文件矛盾时，回到源文件核实，不照抄 AI 的判否理由；补不上的口径先去源文件找，找不到再按问题记录。

### "主观/有争议"判定标准

"主观/有争议"仅指不同专家看到同一证据会得出不同结论的情形（如颜色偏紫还是偏蓝、A还是B）。以下情形不算主观/有争议：

- Prompt 未提及某内容、文件缺失等事实性缺失——这些是事实正确性或信息充足性问题；
- 数值、口径、阈值可以从源文件推出——推不出属于源文件支撑问题。

不得把事实性缺失填成"主观/有争议"来回避判断。

必填和条件必填以当前 `validate()` 为准。已确认模板通常要求：

- “数值/事实”选否时填具体原因；
- “主观/有争议”选是时填具体原因；
- 质量评分必选；
- 问题建议和其他备注不能为空。确实无内容时按页面允许的非空约定填写，但不得用占位语掩盖真实问题。

## 文案与中英文排版

- 页面内可见文案要像熟悉业务的从业者在说明判断：先写具体对象和证据，再写影响和改法；不用空泛结论、整齐重复句式、机械排比或明显模型话术。
- 不批量复制“Rubric可直接使用”“判定依据明确”“暂无内容需补充”等同构句子。即使结论相同，也要说明本条实际核验的文件、数值、状态或路径。
- 中文与相邻ASCII英文、缩写或数字之间不留空格，例如`Dubbo3.2升级`、`2025年6月`、`P99延迟45ms`、`queueId字段`。英文短语内部、代码、命令、文件路径、公式、日志原文和Markdown语法所需空格不得删除。
- 导出前扫描报告正文、任务轨迹、Rubric问题建议、其他备注、题目级理由和建议补充Rubric，清理无必要的中英文边界空格；不得为了清空空格而改动源文件原文、技术标识或文件名。

## Rubric 质量评分语义

- 5：可直接用。数值/口径无误，源文件可核，不同判分者会得到同一结论。
- 4：基本可用。结论成立，仅表述可优化；或存在小问题但 AI/从业者仍能由源文件得到正确过程和答案。
- 3：须修改后可用。口径不清、阈值/条数由 Rubric 自定而非源文件推出，或只有部分支撑。
- 2：严重问题。数值错误、源文件不支撑、只能编造才能得分，或判分依赖主观好恶。
- 1：必须删除或重写。与源文件矛盾、Rubric 自身矛盾，或会惩罚做对的人。

（2026-09-15 复盘会锚点：数值错直接给2分；稀烂到无法使用的给1分；口径/区间/阈值错这类需要源文件推出却推不出的给3分；有小问题但能跑通给4分；一般情况给5分，但不盲给。）

## 题目级评分

当前已见模板包含：

- 可完成性 1-5；
- 难度 1-5；
- 质量 1-5。

三项均必须选分。当前校验器通常在 3 分及以下强制填扣分原因。书面 SOP 还要求难度说明与原数据集标签比较偏高/相符/偏低；如页面有可填字段，应保留该比较。

### 难度锚点（2026-09-15 复盘会）

难度以熟练本岗位从业者为对象，看是否存在跨文件建模、多步测算等行业口径的复杂工作。当前批次多数题目未涉及这类工作，默认给4分；确有跨文件建模或多步测算的给4–5分；因内容仅是信息规整、归集而给3分时，必须写扣分原因。

### 与 Rubric 审核结果的联动（2026-09-15 复盘会）

题目级评分不是与 Rubric 审核无关的独立打分：

- Rubric 错得很多时，总体判定应写"修改后可用"，题目质量给2–3分，不能上面错一片、下面仍给5分或4分；
- Rubric 基本没有错时，不要反向压分——题目质量给3分要能说出理由，说不出就给4分；
- Rubric 错得较多时，可完成性可降到4分或3分，并写出对应原因；
- "质量"项的基准仍是题目真实性、表述清晰度和考察价值；Rubric 对错通过上述联动影响质量分，而不是把每条 Rubric 的对错重复计入。

## 题目级判定

核对当前页面是否要求：

- 任务真实性及不真实原因；
- 文件是否为真实工作文件；
- 明显拼凑、模板残留、机器生成、语言不匹配、年代不符或其他文件问题；
- 信息与约束充足性，以及口径/范围/阈值模糊点；
- 题面文件能否唯一定位；
- 同名文件、多版本副本或同名目录属于题目缺陷还是合理考察；
- 建议补充的 Rubric；
- 总体判定和具体理由。

如当前页面要求在目录树内勾选可定位文件或歧义对象，必须勾选真实路径，不只在文本框中描述。

### 同名文件与多版本勾选（2026-09-15 复盘会）

工作区存在同名文件（如同一基础名既有TXT又有Excel表格）或重复版本时，该勾选的必须勾选，不盲目只勾一个；页面要求填写文件名时，填能区分同名对象的后段（如扩展名或版本后缀），不填无法区分的前缀。

## 跨字段一致性

导出前对同一事实做交叉复核，至少覆盖：

- 同名文件、同名目录或多版本对象是否存在；
- 文件数量、语言/类型、真实性和模板残留结论；
- 目录树勾选、任务轨迹、Rubric 判断、题目级判定和总体理由。

同一事实不得在不同字段同时写成“存在/不存在”“支持/不支持”“真实/不真实”等互斥结论。发现矛盾时回到源文件核验，不用统一改文案的方式掩盖证据冲突。

当两个或以上源文件互相矛盾，且题面、专项规则或后发通知没有指定权威源时，不得由标注员自行选定一个来源后，将相关 Rubric 同时填写为“事实正确、源文件支撑、无争议、质量 5 分”。必须保留冲突，分别判断事实正确性、支撑性和争议性，并在题目级信息充足性或总体判定中反映该冲突。

## 状态与导出

- 页面的自动保存/localStorage 不是最终产物。
- 表单状态优先通过 Chrome DevTools MCP 集成操作真实页面写入，次选 `scripts/cdp/` 或 Computer Use；不得直接修改 HTML、`PRESET_STATE` 或运行代码生成完成态。工作区明确记载的既有轨迹 ID 专项校正仅按其限定范围执行。
- 工作结束时若计时按钮显示“暂停”，先点击暂停；若显示“继续”，说明已暂停，不重复点击。
- “暂存”应导出可继续编辑的 draft HTML。
- “任务完成”只有在校验无错时才导出 shared HTML。
- shared HTML 应固化当前表单状态并进入只读模式。
